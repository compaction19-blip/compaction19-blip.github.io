At a Glance

  • Claude Code 2.1.314 (official changelog date: October 30, 2026) added the permissions.blockWritesOutsideWorkingDirectories setting. The official wording is *"Write, Edit and NotebookEdit refuse paths outside the working directories in every permission mode"*.
  • It blocks writes by 3 file tools: Write, Edit, and NotebookEdit. It is not a "whole-computer lockdown" that also locks down reads, shell commands, and MCP.
  • On Windows, we only verified that the official executable runs as 2.1.314. We could not test actual blocking (verification level: partial).

Before You Begin

  • Required account: You need Claude Pro/Max/Ultra/Team/Enterprise, a Console account, or authentication with a supported external API provider. The free claude.ai plan does not include access to Claude Code. We did not check monthly pricing this time.
  • Version: Write blocking is available in Claude Code 2.1.314 or later. A version is the software's release number. Read blocking (blockReadsOutsideWorkingDirectories) is a separate option available in v2.1.257 or later.
  • Officially supported operating systems: macOS 13+, Windows 10 1809+/Windows Server 2019+, Ubuntu 20.04+, Debian 10+, and Alpine 3.19+ are supported. Requirements include at least 4GB of RAM, x64/ARM64, and an internet connection.
  • Windows note: Git for Windows is recommended but optional. Without it, the PowerShell tool is used.
  • Shell isolation: The shell is the window where you enter commands. Shell sandboxing (an isolated environment) is supported only on macOS/Linux/WSL2. On native Windows, commands run without isolation.

Installation

1. Check the version — 📄 Based on official documentation ① Enter the following in a terminal (the black window where you type commands).

   claude --version

② If you see 2.1.314 or later, you are ready. ③ If your version is older, follow the update instructions for your installation method in the official setup guide. The native installation is officially recommended. The npm method requires Node.js 22+.

2. (Our approach) Check only the executable in an isolated folder — ✅ Tested firsthand ① We left our existing 2.1.303 installation untouched. We downloaded the official 2.1.314 win32-x64 executable into an isolated folder only. We did not run the installer. ② We verified that the SHA256 (file fingerprint) matched and that Authenticode (digital signature) showed Valid. Then we ran the following command.

   bin\claude.exe --version

③ If it prints 2.1.314 (Claude Code) and returns exit code 0, the check is successful. --help also finished with exit code 0.

How to Use It

1. Find and back up your settings file — 📄 Based on official documentation ① Use .claude/settings.json for project settings, ~/.claude/settings.json for user-wide settings, or .claude/settings.local.json for local settings that apply only to you. Be sure to make a copy before editing. ② Once you have found the file, move on to the next step. ③ Do not overwrite its entire contents.

2. Merge one line into permissions — 📄 Based on official documentation (only the JSON syntax was ✅ tested firsthand) ① Add just the line "blockWritesOutsideWorkingDirectories": true inside the existing permissions object. If there is a preceding entry, add a comma at its end. The example below shows the complete structure, including the outer braces, so use it as a reference only if your settings file has no permissions object at all.

   {
     "permissions": {
       "blockWritesOutsideWorkingDirectories": true
     }
   }

Add "blockReadsOutsideWorkingDirectories": true separately only if you also want to block reads. ② We only verified that the example file had no syntax errors by reading it with PowerShell ConvertFrom-Json. We did not apply it to an actual settings file. ③ If you get a JSON error, check the commas and matching braces first.

3. Start a new session — 📄 Based on official documentation Start Claude Code again from the project folder. The folder you start it from becomes the working directory.

4. Test whether blocking works — 📄 Based on official documentation (we did not run this test) ① Create a project folder inside an empty test folder. Start a session inside it. ② Ask Claude to use the Write tool to create the dummy file ../outside.txt in the parent folder. Check both that the tool refuses and that no file is created. ③ Do not ask it to bypass the restriction by writing through the shell. Edit, NotebookEdit, and the auto and bypassPermissions modes need separate tests.

5. Expand access only to external folders you actually need — 📄 Based on official documentation You can expand the working scope with --add-dir, /add-dir, and additionalDirectories. However, we have not yet tested exactly how these interact with the new write-blocking setting.

Our Hands-on Results

Verification level: partial (installation/execution checks only; actual blocking unverified)

We chose this setting for a simple reason. When letting AI modify files, as in auto mode, it could help reduce concerns about accidentally changing another repository. Here is the sequence we followed.

  • Official executable download: 301,388,448 bytes, 6.274 seconds
  • SHA256 match + Authenticode Valid verification: 2.814 seconds
  • --version output 2.1.314 (Claude Code): 0.773 seconds, exit code 0
  • Saved --help output: 0.17 seconds, exit code 0
  • Example JSON syntax check: 0.05 seconds

These times measure the download and verification tasks. They do not measure how long blocking takes.

This is where we got stuck. Actually calling the AI requires login and communication with an external service. But our execution environment allowed only localhost, and the isolated configuration had no login credentials. As a result, we could not compare behavior before and after the setting, test auto or bypassPermissions, or check Recently blocked in /permissions. We did not change permissions to work around these restrictions.

There was another unexpected result. Searching for the new key in the settings reference returned No settings match. This does not mean the feature is absent; it appears that the detailed documentation has not yet caught up with the release. We also ran into some issues along the way. A PowerShell command for logging produced a syntax error once, and the browser blocked opening file://. So we displayed the actual logs again on a temporary localhost page and captured that. Common Pitfalls

  • Assuming "this will lock everything down": It only blocks writes by Write, Edit, and NotebookEdit. For shell isolation, consult the separate official sandboxing guide.
  • Can I just enable /sandbox on native Windows? No. You need WSL2 to use the official shell sandbox on Windows.
  • Assuming read-blocking rules apply unchanged: We cannot yet say that the exceptions and persistence rules documented for read blocking apply to write blocking in exactly the same way.
  • Trying with a free account: You cannot use Claude Code with the free claude.ai plan.

Summary

blockWritesOutsideWorkingDirectories is a new option that prevents file tools from writing outside working folders. Enabling it takes one line. But it is not a whole-computer lockdown. And we have not yet seen it actually block a write. Next time, we will test ../outside.txt blocking in a logged-in environment and add the results.
