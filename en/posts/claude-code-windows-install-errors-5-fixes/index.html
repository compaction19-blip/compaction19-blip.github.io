Before You Start: How to Tell CMD from PowerShell

Windows has two types of command-line windows covered here. The installation commands differ between them, so first check which one you are using.

  1. Search for PowerShell or Command Prompt (명령 프롬프트, CMD) in the Start (시작) menu and open it.
  1. Look just before the blinking cursor. If the prompt starts with PS, as in PS C:\Users\이름>, it is PowerShell. If there is no PS, as in C:\Users\이름>, it is CMD. (📄 From the documentation)
  1. How to know you are ready: If you can identify which window you opened, you are ready to go!

Error 1. Entering the Installation Command in the Wrong Shell

The official documentation provides two Windows installation commands. (📄 From the documentation)

[PowerShell window]
irm https://claude.ai/install.ps1 | iex

[CMD window]
curl -fsSL https://claude.ai/install.cmd -o install.cmd && install.cmd && del install.cmd

✅ Hands-on test — what goes wrong

  1. Entering the PowerShell command in a CMD window produces 'irm' is not recognized as an internal or external command. (To avoid running the actual installation, we entered only the part before | iex and confirmed the same error. The safeguards in our test automation tool also blocked the complete command that downloads and immediately runs the script.)

  1. Once installation finishes, open a new terminal and enter claude --version. If a version number appears, it worked. (📄 From the documentation)

Error 2. 'claude' Is Not Found After Installation (PATH)

✅ Hands-on test — what goes wrong

  1. This time, we used npm to install it in a separate test folder (npm install -g --prefix 시험폴더 @anthropic-ai/claude-code@2.1.314). It finished in 4 seconds, and claude, claude.cmd, and claude.ps1 appeared in the folder.
  1. Several npm warn allow-scripts … warnings appeared during installation, but they did not prevent it from running with npm 11.17.0.

Installing in a test folder with npm (allow-scripts warning) — actual test screen

  1. However, entering claude --version in a new CMD window produced 'claude' is not recognized …, and where.exe claude also returned INFO: Could not find files for the given pattern(s)..

Why? Windows looks for commands only in the folders listed in PATH (the list of folders to search for commands). The installation folder was not on that list.

Fix

  1. After adding the installation folder to PATH in that window and trying again (set "PATH=%PATH%;설치폴더"), we immediately got 2.1.314 (Claude Code). ✅ Hands-on test

Error 2: 'claude' is not recognized → 2.1.314 after adding the folder to PATH — actual test screen

  1. To avoid adding it every time, add it to your user PATH once. According to the documentation, the official installer installs it in %USERPROFILE%\.local\bin. Search for "Environment Variables (환경 변수)" in the Start menu → Path under User variables (사용자 변수) → Edit (편집) → New (새로 만들기) → enter that folder path → OK (확인). (📄 From the documentation and standard Windows procedures; we did not make a permanent PATH change on our PC during this test)
  1. How to confirm it worked: Open a new terminal, then run claude --version → a version number should appear.

Common stumbling block: Even after you add the folder, a window that was already open still will not find it. Be sure to open a new window. (📄 From the documentation)

Error 3. PowerShell Blocks Execution with 'running scripts is disabled'

✅ Hands-on test — what goes wrong

  1. After fixing PATH, we entered claude --version in Windows PowerShell (5.1), which comes with Windows:
claude : File …\npm\claude.ps1 cannot be loaded because running scripts is disabled on this system.
    + CategoryInfo          : SecurityError: (:) [], PSSecurityException

Error 3: claude.ps1 cannot be loaded(running scripts is disabled) — actual test screen

  1. On this PC, all five Windows PowerShell execution-policy scopes (MachinePolicy·UserPolicy·Process·CurrentUser·LocalMachine) were Undefined—in other words, unchanged Windows defaults. We had not deliberately changed them.

Why? npm creates two launcher files for claude: .ps1 and .cmd. PowerShell selected .ps1, but the execution policy blocked that script file.

Fix (✅ We tested options 1 and 2 ourselves)

  1. Easiest option: Use claude.cmd instead of claude. It immediately returned 2.1.314 (Claude Code) in the same window.
  1. Relax the policy only in the current window: Enter Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned -Force first, and claude will work in that window. Closing the window restores the previous behavior.
  1. Recommended in the documentation: Use the PowerShell installer (irm https://claude.ai/install.ps1 | iex) instead of npm. It installs an executable rather than .ps1, avoiding this issue. The documentation also describes changing the user-scope policy to RemoteSigned, but we did not change it because it is a security setting. (📄 From the documentation)

Fixing error 3: claude.cmd / relaxing the policy only in the current window — actual test screen

  1. How to confirm it worked: A version number appears, as in 2.1.314 (Claude Code).

Error 4. 'Not logged in'

✅ Hands-on test

  1. We specified an empty configuration folder with no saved login, as on a newly installed PC, then entered claude -p "한 단어로만 대답해: 안녕". It returned Not logged in · Please run /login.
  1. Asking the same question with our existing logged-in configuration returned "안녕" in 2 seconds.

Error 4: Not logged in → a response with the logged-in configuration — actual test screen

Fix (📄 From the documentation)

  1. Run claude on its own in the terminal.
  1. Enter /login, then log in to your Claude account in the browser that opens. If the browser does not open, press c to copy the login URL and paste it into your browser.
  1. How to confirm it worked: Ask a question again and check that you receive a response.

Common stumbling block: Claude Code cannot be used with the free claude.ai plan (you need a paid plan such as Pro or Max, or a Console account). (📄 From the documentation)

Error 5. 'Invalid API key' (A Leftover Environment Variable)

✅ Hands-on test

  1. To simulate a PC with an old ANTHROPIC_API_KEY environment variable set for another tool, we supplied a fake key (no charges incurred) and asked a question.
  1. Result: Alongside Invalid API key · Fix external API key, we saw ANTHROPIC_API_KEY or another auth source is set and takes precedence over your claude.ai login—a warning that this key takes precedence over the claude.ai login.
  1. Asking again in a window without the variable returned "안녕" using the subscription login (2.1 seconds).

Error 5: Leftover ANTHROPIC_API_KEY (fake key) → Invalid API key — actual test screen

Fix

  1. Enter set ANTHROPIC_API_KEY in CMD. If you see Environment variable ANTHROPIC_API_KEY not defined, the variable is not set. ✅ Hands-on test
  1. If a value appears, go to "Environment Variables" from the Start menu → delete ANTHROPIC_API_KEY from User variables/System variables (시스템 변수), then open a new window. (Standard Windows procedure)

Caution: If the key is valid, it will work without an error. That means you could be using the key rather than your subscription login without realizing it, so it is worth checking.

When You Get Stuck, Start with claude doctor

claude doctor is a read-only diagnostic command that shows the installation status without starting a session. (📄 From the documentation) In our test installation, it displayed Running: npm-global (2.1.314), the installation path, and the automatic update status, then ended with No installation issues found.. ✅ Hands-on test

Limitations to Keep in Mind

  • We reproduced each error once, on a single Windows 11 PC with English as its display language. On a Korean-language Windows installation, error messages may appear in Korean.
  • We reproduced the installation using npm. We did not run the officially recommended PowerShell/CMD installers because Claude Code was already installed on this PC.
  • We used Node 26.5.0 and npm 11.17.0 from the Aside execution environment. The npm 12 claude native binary not installed error described in the documentation did not occur in this test, so we checked it only in the documentation.
  • We simulated 'Not logged in' with an empty configuration folder, so we did not reproduce an actual login expiration.
  • We checked the API key issue only with a fake key, and did not test in a PowerShell 7 window.
  • We did not cover network errors such as corporate proxies, certificates, or antivirus blocking.
